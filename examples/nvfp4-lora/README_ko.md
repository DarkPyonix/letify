# 빌린 카드에서 NVFP4 LoRA

이 프로젝트가 존재하는 이유가 되는 시나리오입니다. 손에 있는 것은 6 GiB GPU가 달린 노트북이고,
돌려야 하는 모델은 96 GiB를 요구합니다. RTX PRO 6000 Blackwell을 Colab 컴퓨팅 단위로 빌리면
시간당 약 975원이고 같은 카드가 Modal에서는 시간당 약 4,070원입니다. 싼 쪽을 쓸 이유는 충분한데,
불편한 것은 학습이 아니라 그 주변입니다. 세션 켜기, 환경 설치, 데이터 옮기기, 체크포인트 보관,
그리고 아무것도 안 하면서 한 시간을 청구하기 전에 세션 끄기.

이 네 개의 스크립트가 없애는 것이 그 주변입니다. [recipe.py](recipe.py)의 학습 코드는 letify를
한 번도 언급하지 않습니다.

## 실행

계정도 설정도 필요 없는 local 프로바이더로 시작합니다.

```bash
python 00_smoke.py --provider local
python 01_sweep.py --provider local --steps 20
python 02_resume.py --provider local
python 03_watch.py --provider local
```

그다음 계정 하나를 등록하고 플래그 하나만 바꾸면 같은 스크립트가 빌린 카드를 향합니다.

```bash
letify login colab colab_pro --account you@example.com
python 00_smoke.py  --provider colab_pro --device G4
python 01_sweep.py  --provider colab_pro --device G4
```

번호는 튜토리얼의 장 번호가 아니라 실행할 가치가 있는 순서입니다.

| 스크립트 | 목적 | 확인되는 것 |
|---|---|---|
| [00_smoke.py](00_smoke.py) | 돈을 쓰기 전 호출 한 번 | 프로바이더가 응답하고, 환경이 설치되고, 이 프로젝트 코드가 도착했고, 카드가 결제한 그 카드인지 |
| [01_sweep.py](01_sweep.py) | 풀링된 세션에 여섯 설정 | 선언된 탐색 공간, 슬롯당 따뜻한 세션 하나, 최선 어댑터를 저장소에 보관 |
| [02_resume.py](02_resume.py) | 선점 후 이어서 학습 | 새 세션 안에 체크포인트를 되돌려 놓기, 움직이는 이름 뒤의 불변 블롭 |
| [03_watch.py](03_watch.py) | 돌아가는 동안 비용 감시 | 계정 잔여 사용량, 그리고 카드가 실제로 바쁜지 |

## 각 조각이 하는 일

**선언은 실행 위치가 등장하는 유일한 곳입니다.** `recipe.train`은 torch를 임포트하고 딕셔너리를
반환하는 평범한 함수입니다. `let.function(device=..., host=...)`이 어디서 돌릴지 정합니다. 그래서
노트북에서 디버깅하는 파일과 빌린 카드에서 도는 파일이 같고, `--provider local`이 모의가 아니라
실제 검증이 됩니다.

**`ship("recipe")`가 학습 코드를 값으로 보냅니다.** 저쪽 머신은 `uv.lock`이 지정한 것만 설치하고
이 프로젝트의 사본은 없으니, `recipe.py`에서 임포트한 함수는 호출 안에 실려 가야 합니다. 락 파일이
설치하는 것은 이름으로 갑니다. torch를 매 호출마다 네트워크로 보내는 것은 말이 안 되기 때문입니다.

**`lifetime="process"`가 스윕을 감당 가능하게 만듭니다.** 세션 시작, 환경 설치, 첫 전송은 모두 GPU
시간으로 청구됩니다. 기본값 `"call"`이면 여섯 지점이 그 비용을 각각 다시 냅니다. 짧은 실행에서는
준비 비용이 학습 비용보다 큽니다.

**스윕이 얼마나 넓게 도는지는 프로바이더의 인벤토리**이고 인자가 아닙니다. 계정이 가진 것을 선언하면
그것이 폭입니다.

```toml
[colab_pro.devices]
G4 = { count = 2 }
```

카드 두 장이면 총 GPU 비용은 그대로 두고 벽시계 시간이 절반이 됩니다. 카드를 두 장 동시에 쓰는 실행은
`device=lab.A100 * 2`로 요청하고, 네 장짜리 머신에서는 세션 네 개가 아니라 두 개입니다. 선언에 적는
숫자로는 이것을 말할 수 없습니다.

**볼륨은 마운트된 디스크가 아니라 내용 주소 저장소입니다.** `absorb`는 세션에서 파일을 꺼내 이름
아래 보관하고, `resume`은 이름이 가리키는 것을 세션 안에 되돌려 놓습니다. 둘 다 세션이 아니라 선언을
받습니다. 어느 세션에서 호출이 돌았는지는 letify가 아는 것이고, 다른 세션을 지목하면 파일이 없는 세션을
읽게 됩니다. 블롭은 불변이고 이름은
수십 바이트라서 두 세션이 동시에 써도 서로의 결과를 잃지 않습니다. 이름 하나가 이기고 체크포인트는
둘 다 남습니다.

**해제할 것이 없습니다.** 호출은 자기 세션을 끝내고, `lifetime="process"`는 프로세스가 끝나거나
유휴 수거기가 가져갈 때까지 유지하며, 하트비트 리스가 있어서 스크립트가 죽어도 GPU가 계속 청구되지
않습니다. 지속성은 저장소의 체크포인트이고, 나보다 오래 사는 세션이 아닙니다.

## 두 실행 방식, 그리고 여기서 쓸 것

`00_smoke.py`가 판단 근거인 산수를 출력합니다. CUDA 호출 중계는 파이썬과 데이터를 여기 두고 드라이버
호출만 보내므로, 비용은 호스트가 값을 읽어 오는 지점마다 네트워크 왕복 한 번입니다. 직접 실행 대비
효율은 `T / (T + k * RTT)`이고, `T`는 스텝당 GPU 시간, `k`는 스텝당 호스트 동기화 횟수입니다.

Colab 런타임까지 150 ms 링크에서:

| 스텝 시간 | k = 3 (기본 루프) | k = 1 (조정 후) |
|---|---|---|
| 0.05초, 디코딩 스텝 | 10% | 25% |
| 0.5초, NVFP4 마이크로 스텝 | 53% | 77% |
| 4초, 큰 배치 | 90% | 96% |

그래서 학습의 기본은 `host="remote"`이고 이 스크립트들이 쓰는 것도 그쪽입니다. `host="local"`은
데이터가 이 머신을 떠나서는 안 될 때 의미가 생기고, `recipe.train`은 그에 맞게 쓰여 있습니다. 손실을
매 스텝이 아니라 열 스텝에 한 번 읽는데, 0.5초 스텝을 절반에서 거의 전부로 올리는 단 하나의 변경이
바로 그것입니다. 토큰 단위 디코딩은 어떤 실용적 지연에서도 나쁩니다. 왕복이 상한을 정하기 때문입니다.

## 무엇이 합성이고 무엇이 아닌지

데이터는 의도적으로 합성입니다. 실제 데이터셋은 예제를 다운로드와 토크나이저와 라이선스에 의존하게
만들고, 여기서 보여주는 것은 인프라입니다. `recipe.train`에서 `inputs`와 `targets`를 만드는 두 줄을
데이터로더로 바꾸면 나머지는 실제로 돌릴 코드 그대로입니다.

양자화도 대역입니다. `recipe.train`은 베이스 가중치를 좁은 타입으로 보냈다가 계산 dtype으로
되돌립니다. Blackwell 커널이 없어도 weight-only 양자화의 정확도 비용을 보여주기 위한 것입니다.
컴퓨팅 능력이 10.0 미만인 카드에서는 `00_smoke.py`가 아닌 척하지 않고 그렇다고 말합니다.

나머지는 전부 실제입니다. 실제 세션, 실제 프레임 파이프 뒤의 실제 워커 프로세스, 실제 내용 주소
저장소, 실제 체크포인트 왕복입니다.
