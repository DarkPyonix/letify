## 문제를 표 하나로

휘발성 프로바이더에서는 매 세션이 같은 것을 다시 만듭니다. 그 시간 전부가 GPU 크레딧으로 청구됩니다.

| 20GB 모델 캐시 받기 | 시간 |
|---|---|
| 🐢 연구실 서버에서 100Mbps로 | 약 27분 |
| 🚶 Hugging Face 허브에서 | 3~5분 |
| 🚀 런타임 옆 버킷에서 | **40~60초** |

90분 세션이면 첫 줄은 크레딧의 30%를 기다리는 데 쓰는 것이고, 셋째 줄은 1%입니다.

## 환경

`Env`는 원격 환경을 선언합니다. lock 파일의 해시로 키가 정해지므로, 같은 선언 두 개는 풀링된 런타임과 캐시된 아카이브를 공유합니다.

```python
env = letify.Env()                        # uv.lock
env = letify.Env.from_lock("train.lock")  # 다른 lock 파일
env = env.pip_install("flash-attn")       # lock 파일에 없는 패키지
env = env.run("apt-get install -y git")   # 설치 후 실행할 명령
env = env.vars(HF_HOME="/opt/cache")      # 런타임의 환경 변수
```

### uv.lock을 쓰고 pip freeze를 안 쓰는 이유

uv lock 파일은 uv가 지원하는 **모든** 플랫폼에 대해 마커와 함께 해석됩니다. 그래서 lock 파일 하나로 Windows나 macOS 클라이언트에서 Linux 런타임을 구성할 수 있습니다.

`pip freeze` 목록은 그렇지 않습니다. 그것을 만든 머신의 핀을 담고 있어서 플랫폼 전용 패키지가 섞이고, Windows 목록은 Linux에 설치되지 않습니다.

### 어떤 모듈이 호출과 함께 가나

lock 파일에 있는 패키지는 런타임에 설치되고 이름으로 참조됩니다. 내가 쓴 코드는 lock 파일에 없으니 호출과 함께 가야 합니다. 원격에는 그게 없거나 예전 버전이 있기 때문입니다.

letify가 lock 파일을 보고 판단합니다. 필요할 때만 덮어쓰세요.

```python
env = env.ship("mypkg")     # 이 모듈을 내용으로 보냅니다
```

그래서 코드를 고치고 다시 돌리는 것이 쌉니다. 코드는 수백 KB이고, 비싼 것은 환경과 데이터이며 그건 캐시됩니다.

## 볼륨

볼륨은 프로바이더의 저장소 위에 놓인 내용 주소 블롭 저장소입니다.

```python
cache = colab.volume("hf-cache")

@let.function(device=colab.G4, host="remote", env=env, volumes=[cache])
def train(lr): ...
```

이 한 줄이 휘발성 프로바이더를 persistent처럼 동작하게 만듭니다.

### 파일 동기화가 아니라 내용 주소 방식인 이유

| | 🐌 양방향 동기화 | ⚡ 내용 주소 방식 |
|---|---|---|
| 두 세션이 쓸 때 | 마지막이 이기고 나머지 작업은 사라짐 | 내용이 다르면 이름이 달라서 충돌 불가 |
| 이미 있는지 확인 | 크기와 수정 시각 비교 | 해시를 가진 것이 **곧 증거** |
| 작은 파일 5만 개 | 왕복 5만 번 | 묶음 하나, 전송 한 번 |
| 실패 후 재시도 | 전체를 다시 나열 | 이미 저장된 것을 이름으로 건너뜀 |

바뀌는 이름은 별도의 ref 공간에 둡니다. Git의 객체와 브랜치 이름과 같은 구조입니다. ref는 수십 바이트라 경쟁이 나도 무해하고 두 블롭 모두 남습니다.

### 묶는 단위가 주는 이득

여기가 실제로 빠르게 만드는 부분이고, 세부 사항이 아니라 결정입니다.

**큰 파일은 그대로 둡니다.** 모델 샤드는 이미 크니 파일당 지연이 문제가 되지 않습니다.

**작은 파일 트리는 묶습니다.** 가상 환경은 파일 수만 개입니다. lock 파일 해시를 키로 아카이브 하나로 묶으면 왕복 수만 번이 전송 한 번이 됩니다.

못 하는 것도 분명히 해두겠습니다. 첫 전송의 바이트 수는 그대로입니다. 개선되는 것은 메타데이터 교환으로, 파일마다 요청하는 대신 매니페스트 한 번 읽기가 되고, 그리고 반복 전송은 이름으로 건너뜁니다.

### 볼륨 사용

```python
cache = colab.volume("hf-cache")

cache.cached_env(env)                 # 미리 만든 환경의 digest, 없으면 None
cache.cache_env(env, "/opt/venv")     # 하나 만들어서 이 env 키로 기억

cache.put_checkpoint("run-1", "/tmp/ckpt")   # 저장하고 ref를 옮김
cache.fetch_checkpoint("run-1", "/tmp/ckpt") # 그 이름의 최신, 없으면 None
cache.latest_checkpoint("run-1")             # digest만
```

백엔드나 위치를 덮어쓰려면 이렇게 합니다.

```python
cache = colab.volume("hf-cache", bucket="my-bucket", prefix="letify")
cache = lab.volume("scratch", backend="filesystem", root="/mnt/data/letify")
```

## 백엔드

프로바이더가 고르므로 선언에는 나오지 않습니다.

| 백엔드 | 쓰는 곳 | 이유 |
|---|---|---|
| `filesystem` | `Local`, `Shell`, `Elice` | 디렉터리. 내 머신이 다른 쪽이 당겨가는 원본이 될 수 있습니다. 엘리스에서는 머신 자체 디스크입니다. |
| `gcs` | `Colab` | Colab 런타임은 Compute Engine VM이라 내부 전송입니다. |
| `modal` | `Modal` | 컨테이너 옆에 마운트되는 Modal 볼륨. |

> 🌏 **Colab에서는 `US` 같은 멀티리전 버킷을 쓰세요.** Colab 런타임이 어디 뜨는지 고를 수 없고, 멀티리전이면 읽을 때마다 리전 간 요금이 붙는 것을 막아줍니다. 그 참에 결제 알림도 걸어두세요.

## Google Drive를 안 쓰는 이유

드라이브는 마운트하면 디스크처럼 보이고, 거기서 오해가 생깁니다. 실제로는 파일 단위로 접근하는 소비자용 파일 서비스이고, 파일 크기와 무관하게 접근마다 수십에서 수백 밀리초의 HTTP 요청이 나갑니다.

계산해보면, 이미지 5만 장에 100ms씩이면 epoch당 순수 입출력만 한 시간이 넘고 그동안 GPU 사용률은 10~20%입니다. 같은 데이터를 아카이브 하나로 한 번 받아 로컬에 풀면 1분 미만입니다.

드라이브는 창고로는 괜찮습니다. 작업 디스크가 아닙니다. 이미 거기 데이터가 있다면 학습 중에 읽지 말고 세션 시작에 아카이브 하나를 당겨오세요.

## 호출이 읽는 데이터

로컬 데이터는 `pathlib.Path`로 가리키면 letify가 호출과 함께 보냅니다. `Path` 인자, `Path` 기본값, 함수가 읽는 전역 변수나 클로저의 `Path`를 호출을 피클할 때 찾아냅니다. 함수 본문은 파일 이름과 디렉터리 구조가 같은 런타임 쪽 `Path`를 받습니다.

```python
DATA = Path("data/corpus")

@let.function(device=lab.A100, host=letify.remote)
def train(lr):
    files = sorted(DATA.rglob("*.bin"))   # 런타임에 있는 디렉터리
```

찾아내는 대상은 프로젝트 루트(가장 가까운 `pyproject.toml`이 있는 디렉터리)나 `[tool.letify] data_roots`에 적은 디렉터리 아래에 있는 파일과 디렉터리, 그리고 아직 없는 경로입니다. 그 루트 밖의 경로와 프로젝트 루트 자체는 그대로 평범한 경로로 남습니다. 디렉터리 안의 `.git`, `.venv`, `__pycache__`는 건너뜁니다.

파일마다 해시는 한 번만 계산하고 크기, 수정 시각, inode와 함께 `~/.cache/letify/digests.json`에 기억하므로, 바뀌지 않은 데이터셋은 다시 읽지 않습니다. 바이트를 어디서 가져오는지는 계정에 따라 다릅니다.

| 계정 | 첫 세션 | 이후 세션 |
|---|---|---|
| persistent (`persistent = true`, Modal, local) | 없는 파일만 링크로 전송 | 업로드 없음. 런타임 디스크에 이미 있음 |
| `bucket = "<이름>"`이 있는 ephemeral | 없는 파일을 버킷에 올리고 런타임이 받음 | 업로드 없음. 런타임이 버킷에서 받음 |
| `bucket`이 없는 ephemeral | 모든 파일을 링크로 전송 | 매번 모든 파일을 다시 전송 |

바뀐 파일은 그 파일만 다시 보냅니다. 데이터를 보낸 호출마다 한 줄이 찍힙니다. 예: `letify: data 1024 files 1024.0 MiB detected, 0 files 0.0 MiB already on the runtime, sent 512 files 512.0 MiB before the call in 5.9 s, 512 files 512.0 MiB during it in 5.8 s (88.1 MiB/s), first access waited 0.0 s`.

첫 번째 물결에 해당하는 데이터가 런타임에 올라가면 호출이 바로 시작되고, 나머지는 호출이 도는 동안 도착합니다. 첫 번째 물결은 피클된 호출에서 뽑아낸 전송 순서의 앞부분이며 512 MiB 또는 256개 파일에서 끊습니다. 인자에 담긴 `Dataset`이나 경로 목록은 순서를 그대로 알려 주고, `DataLoader`의 샘플러는 섞인 epoch 순서를 알려 주며, 그것들이 가리키지 않는 경로는 함수 코드의 읽기 호출 위치로 정합니다. 나머지는 매니페스트 순서입니다. 한계값은 계정의 `data_first_wave_mib`와 `data_first_wave_files`로 바꾸고, 순서를 직접 정하려면 `@let.function(data_order=..., data_first_wave=...)`를 쓰면 분석보다 우선합니다.

호출이 시작된 다음의 순서는 런타임이 실제 읽기를 관찰해서 정합니다. 감싼 `DataLoader`가 샘플러를 64배치 앞서 읽고, `Dataset.__getitem__`은 요청받은 항목을 알리며, `open`은 순차 훑기가 건드린 파일을 알립니다. 계정에 `data_observe = false`를 적으면 셋 다 끕니다.

함수 본문은 절반만 쓰인 파일을 보지 않습니다. 디렉터리 목록과 `Path.stat()`은 바이트가 도착하기 전에도 매니페스트로 답하므로 `iterdir`와 `glob`은 첫 스텝부터 완전하고, 아직 도착하지 않은 파일을 열 때만 기다립니다. 기다렸다는 것은 예측한 순서가 틀렸다는 뜻이고, letify가 그렇다고 알립니다. 예: `letify: data waited for 3 files 12.0 MiB not sent in time, 1.4 s total, first 0042.bin`. 끝내 도착하지 않은 블롭은 `data_wait_timeout`초(기본 600) 뒤에 그 읽기를 실패시킵니다.

런타임은 이 파일들을 `<workspace root>/data/blobs`에 예산 안에서 보관합니다. 예산은 50 GiB와, 캐시가 쓸 수 있는 디스크 공간의 절반 중 작은 값이며, 계정에 `data_cache_gib = <GiB>`를 적으면 그 값입니다. 새 파일을 보내거나 돌려받은 호출이 끝나면, 실행 중인 호출이 쓰지 않는 파일을 가장 오래 안 쓴 것부터 지우고 한 줄로 알립니다. 예: `letify: data cache evicted 120 files 4096.0 MiB in 0.1 s, 51200.0 MiB of 50.0 GiB in use`. 최근 10분 안에 쓴 파일은 지우지 않으므로, 잠시 예산을 넘을 수 있습니다.

`letify cache`는 persistent 프로바이더마다 런타임 캐시 크기를 보여 주고, `~/.cache/letify/digests.json`에서 이제 없는 파일의 항목을 지웁니다. `letify cache clear <별칭>`은 그 프로바이더의 런타임 캐시를 비웁니다. ephemeral 프로바이더는 세션 사이에 보관하지 않는다고 표시됩니다.
### 호출이 쓴 파일

디렉터리와 아직 없는 경로는 출력 위치입니다. 호출이 정상적으로 반환되면, 함수 본문이 그곳에 새로 만들거나 바꾼 파일이 같은 상대 경로로 로컬에 복사됩니다.

```python
RUN = Path("runs/exp1")

@let.function(device=lab.A100, host=letify.remote)
def train(epochs):
    RUN.mkdir(parents=True, exist_ok=True)
    torch.save(model.state_dict(), RUN / "model.pt")   # 호출이 끝나면 로컬 runs/exp1/model.pt
```

- 내용이 바뀌지 않은 파일은 보내지 않습니다. 로그만 바꾼 두 번째 호출은 로그만 받습니다.
- 예외로 끝난 호출은 아무것도 쓰지 않습니다.
- 런타임에서 지운 파일은 로컬에서 지우지 않습니다.
- 같은 로컬 경로에 동시에 쓰는 호출은 차례로 반영되고, 같은 파일은 나중에 끝난 호출의 내용이 남습니다. 파일이 반쯤 섞이는 일은 없습니다.
- 디렉터리 안의 파일은 런타임 캐시를 가리키는 하드 링크로 놓이고, 본문이 쓰기 모드로 여는 순간 그 파일만 사본이 되므로, 본문이 기존 파일을 덮어써도 되고 읽기만 하는 호출은 아무것도 복사하지 않습니다. 본문이 시작한 프로그램(`sh`, `ffmpeg` 등)은 읽기 전용 링크를 보므로 root가 아니면 제자리에서 쓸 수 없습니다.

호출마다 한 줄이 더 찍힙니다. 예: `letify: data wrote back 3 files 512.1 MiB in 2.4 s (213.4 MiB/s), 0 files 0.0 MiB already on the client`.

## 옮기기에 너무 큰 데이터

세 가지 방법을 시도할 순서대로 적습니다.

**한 번 묶어서 보내기.** 아카이브 하나, 병렬 다운로드, 로컬 디스크에 풀기. 단순하고 예측 가능하며, 데이터가 들어가고 epoch를 여러 번 돌면 이게 정답입니다.

**샤드로 스트리밍.** URL로 읽는 tar 샤드로 두면 학습이 바로 시작되고 다운로드가 계산과 겹칩니다. prefetch 깊이를 2 이상 줘서 왕복을 가리고, 샤드는 200~500MB로 유지하세요. 대가는 셔플이 근사치가 되고 epoch마다 다시 전송된다는 점입니다.

**원본을 가까이 옮기기.** 데이터셋을 런타임과 같은 인프라에 둡니다. 클라우드 백엔드의 볼륨이 해주는 일이 이것입니다.

스트리밍 쪽 계산입니다. 224×224 JPEG 100KB, A100이 초당 500장을 처리하면 50MB/s가 필요합니다. 1Gbps 회선이면 여유가 있습니다. 배치를 두 배로 하면 100MB/s가 필요해지고 회선이 병목이 됩니다.
