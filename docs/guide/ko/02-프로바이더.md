## 모델

프로바이더 객체는 **하나의 인프라 종류에 있는 하나의 계정**입니다. 설정 파일에 한 번 선언하고 alias로 꺼내 씁니다.

```python
let = letify.Launcher()

colab = let.providers.colab_a      # 구글 계정 하나
lab   = let.providers.lab_a100     # 머신 하나
here  = let.providers.local        # 항상 존재, 선언 불필요
```

GPU는 프로바이더의 속성이고, 그 값이 선언에 필요한 모든 것을 담고 있습니다.

```python
@let.function(device=colab.G4, host="remote")
def train(lr): ...
```

`colab.G4` 하나에 프로바이더, 계정, GPU, CPU 배치가 들어 있습니다. 이 넷은 하나의 결정이라서 하나의 인자입니다.

## 설정이 있는 곳

letify는 상태를 역할이 다른 `.letify` 디렉터리 두 곳에 둡니다.

| 경로 | 담는 것 | Git 추적? |
|---|---|---|
| `~/.letify/config.toml` | 이 머신의 모든 계정: kind와 접속 정보, 비밀은 없음 | 아니오, 저장소 밖입니다 |
| `~/.letify/accounts/<alias>/` | 그 계정의 자격 증명, 소유자만 접근 | 아니오 |
| `<project>/.letify/config.toml` | 프로젝트 기본값, 프로젝트가 쓰는 계정의 alias | 예 |

홈 파일은 이 머신에 있는 계정의 목록입니다. 프로젝트 파일은 그중에서 고릅니다. 계정은 다음 중 하나일 때만 프로젝트에서 쓸 수 있습니다.

1. 프로젝트 파일이 그 이름을 적었습니다. 빈 테이블로 충분합니다.
2. 홈 항목에 `global = true`가 있습니다.
3. `local`입니다. 항상 쓸 수 있습니다.

```toml
# 프로젝트의 .letify/config.toml, 커밋됨
[colab_a]         # 홈 계정 colab_a를 설정 그대로 사용
[lab_a100]
```

프로젝트 테이블에 적은 필드는 홈 항목의 같은 필드를 덮어씁니다. 다른 사람은 저장소를 받아 거기 적힌 alias에 대해 `letify login`을 실행하면 됩니다.

## 비밀

자격 증명은 어느 `config.toml`에도 들어가지 않습니다. `letify login`이 묻고 저장합니다.

```bash
letify login elice elice_a100      # ~/.letify/accounts/elice_a100/access_token에 기록
letify logout elice_a100           # 계정을 지우고 그 디렉터리도 삭제
```

`access_token` 같은 필드는 다음 순서로 해소됩니다.

1. `access_token_env`가 가리키는 환경 변수.
2. 파일 `~/.letify/accounts/<alias>/access_token`. 권한 0600으로 만들어집니다.
3. 홈 항목의 리터럴 값. 비밀이 아닌 기본값에만 씁니다.

```toml
[elice_a100]
kind = "elice"
access_token_env = "ELICE_ACCESS_TOKEN"        # 선택, 저장된 파일보다 우선
```

OS 키링은 쓰지 않습니다.

## 📓 Colab

```toml
[colab_a]
kind = "colab"
account = "you@example.com"
```

공식 Colab CLI를 쓰므로 터널이 필요 없고 약관 위험도 없습니다. 세션은 `colab new`로 만들고 `colab stop`으로 내리며, 백그라운드 데몬이 브라우저 탭 없이도 런타임이 유휴 종료되는 것을 막아줍니다.

| | |
|---|---|
| GPU | `T4`, `L4`, `G4`, `A100`, `H100`, TPU는 `v5e1`, `v6e1` |
| `G4`는 | RTX PRO 6000 Blackwell, 96GB. `RTX_PRO_6000`도 alias로 인정 |
| 저장소 | **휘발성.** 런타임을 바꾸면 새 머신에 빈 디스크입니다 |
| 실행 방식 | 함수 전송만 |
| 캐시 백엔드 | Google Cloud Storage |

두 가지를 알아두세요. GPU는 Pro 또는 Pro+ 권한이 필요하고, 원격 제어 기능은 컴퓨트 유닛 잔액이 양수인 동안 허용됩니다. 잔액이 소진되면 계정이 무료 티어 정책으로 돌아가고, 그 정책은 이 기능들을 금지합니다.

여기서 `host="local"`은 예외를 던집니다. 제어 경로가 구글 프론트엔드를 거쳐서 한국에서 왕복이 150~200ms이고, 그러면 파인튜닝은 절반, 추론은 몇 퍼센트만 남습니다. 예외 메시지에 그 내용이 그대로 들어 있습니다.

## 🐚 Shell, 연구실이나 학교 서버용

```toml
[lab_a100]
kind = "shell"
address = "gpu.lab.example.edu"
user = "researcher"
key = "~/.ssh/id_ed25519"
persistent = true
```

| 옵션 | 역할 |
|---|---|
| `address`, `user`, `port`, `key` | 표준 SSH 접속 정보 |
| `jump` | 점프 호스트, `ssh -J`로 전달 |
| `persistent` | 세션 사이에 디스크가 유지된다고 선언 |
| `gpus` | 목록. 탐색 시 접속을 건너뜁니다 |
| `port_command` | 현재 포트를 출력하는 명령. 포트가 바뀌는 호스트용 |
| `store` | 캐시 백엔드 덮어쓰기 |
| `workspace` | letify가 머신에서 쓰는 단 하나의 디렉터리. 프로젝트 `.venv`, 볼륨 데이터, 임시 파일이 모두 여기 들어갑니다. 기본값 `~/.letify-runtime`. 홈 파일에만 씁니다 |

**저장소 수명의 기본값은 휘발성이고, 일부러 비관적으로 잡았습니다.** 실제로는 디스크가 남는데 휘발성으로 가정하면 시간만 더 들고 작업은 성공합니다. 반대로 남지 않는데 persistent로 가정하면 바로 실패합니다.

머신이 홈 디렉터리를 유지한다는 것을 확인하면 `persistent = true`를 넣으세요. 연구실 서버라면 보통 그렇습니다. 그러면 기본 실행 방식이 함수 전송으로 바뀝니다.

`gpus`를 선언하면 import 시점에 SSH가 붙지 않습니다.

```toml
gpus = ["A100", "A100", "A100", "A100"]
```

어떤 서버는 `/workspace` 같은 특정 디렉터리 아래에만 쓰기를 허용합니다. `letify login shell`은 키가 통하는 것을 확인한 직후 letify가 쓸 위치를 묻고, root 없이 그 디렉터리를 만들고 쓸 수 있는지 SSH로 확인합니다. 확인에 실패하면 아무것도 쓰지 않고 오류를 알려줍니다.

```
$ letify login shell lab_a100 --address gpu.lab.example.edu
Workspace root on gpu.lab.example.edu [~/.letify-runtime]: /workspace/researcher/letify
```

스크립트에서는 `--no-input`과 함께 `--workspace /workspace/researcher/letify`를 넘기세요. 이미 선언된 계정의 위치를 바꾸려면 `--workspace`를 붙여 로그인을 다시 실행합니다. 새 경로를 확인한 뒤에 기록합니다. `letify check lab_a100`은 `workspace <path>: writable` 또는 쓸 수 없는 이유를 출력합니다.

devices 테이블은 `letify login shell`이 대신 써 줍니다. 키가 통하는 것을 확인한 직후 머신에서 `nvidia-smi`를 한 번 실행하고, 찾은 카드를 보여준 뒤 letify가 쓸 인덱스를 묻습니다. 빈 칸으로 두면 전부 씁니다.

```
$ letify login shell lab_a100 --address gpu.lab.example.edu
A100: 4 cards, indices 0-3 (80 GB each)
RTX_PRO_6000: 2 cards, indices 4-5 (96 GB each)
Indices letify may use for A100 [0-3]: 0,1
Indices letify may use for RTX_PRO_6000 [4-5]:
```

```toml
[lab_a100.devices]
A100 = { indices = "0-1" }
RTX_PRO_6000 = { indices = "4-5" }
```

스크립트에서는 `--no-input`이 모든 카드를 기록하고, `--indices A100=0-1`(여러 번 가능)이 이름 하나의 인덱스를 좁힙니다. `nvidia-smi`가 없거나 GPU를 찾지 못해도 로그인은 성공합니다. 이때는 아무것도 기록하지 않고, letify가 처음 쓸 때 머신에 묻습니다. 이미 선언된 계정은 다시 묻지 않습니다. `letify login shell lab_a100 --detect-devices`는 머신에 다시 묻고, 확인을 받은 뒤 테이블을 바꿉니다. 테이블은 평범한 TOML이라 직접 고쳐도 됩니다.

## 🕳️ Tunnel, NAT 뒤의 머신용

인바운드 연결을 받을 수 없는 머신용입니다. letify는 [Tailcat](https://github.com/tailscale/tailcat)으로 이 머신에 붙습니다. Tailcat은 계정도 자체 서버도 필요 없습니다. 작업은 여전히 SSH가 합니다.

설정은 머신마다 하나씩, 명령 두 개입니다. 두 머신 모두 `tailcat`이 필요하고, 원격 머신에는 letify와 SSH 서버가 필요합니다.

**1. 원격 머신에서** 에이전트를 시작합니다.

```bash
letify client shell connect --name home_box
```

`tailcat`이 없으면 [tailcat과 eci 설치](#tailcat과-eci-설치)대로 설치합니다. 자동 설치를 꺼 두었거나 SSH 서버가 없으면 그 머신에 맞는 설치 방법을 그대로 출력하고 종료합니다. 둘 다 있으면 내 머신에서 실행할 명령 하나를 출력합니다.

```
letify login tunnel home_box --connect eyJ0YWlsY2F0Ijoi...
```

에이전트는 계속 실행해 두세요. 예를 들어 `tmux` 안에서 띄우면 됩니다. 모든 연결이 에이전트를 거치고, 다시 시작하면 주소가 바뀌어 새 토큰으로 로그인을 다시 해야 합니다.

**2. 내 머신에서** 출력된 명령을 실행합니다.

```bash
letify login tunnel home_box --connect eyJ0YWlsY2F0Ijoi...
```

`letify login shell`과 똑같이 Tailcat을 통해 SSH 키를 설치하고(원격 비밀번호를 한 번 입력합니다), 키를 확인하고, 워크스페이스 루트를 점검하고, GPU를 기록합니다. 그다음 `letify check home_box`로 머신이 응답하는지 확인합니다. `~/.letify/config.toml`에 쓰이는 계정은 주소 없이 이렇게 생깁니다.

```toml
[home_box]
kind = "tunnel"
tailcat = "tc..."
tailcat_port = 40123
user = "researcher"
port = 22
key = "~/.ssh/id_letify"
```

더 단순한 경로를 먼저 시도하세요. 직접 주소, 그다음 점프 호스트, 그다음 터널입니다. 학교 머신은 앞의 두 개가 되는 경우가 많습니다. 상세한 측정치는 [docs/NETWORK.md](../../NETWORK.md)에 있습니다.

## ☁️ Modal

```toml
[modal_lab]
kind = "modal"
```

계정마다 한 번 로그인합니다.

```bash
letify login modal modal_lab
```

letify가 선택 사항인 Modal 프로필을 묻고(로그인할 Modal 워크스페이스를 가리키며, 스크립트에서는 `--profile`), uv로 Modal의 `modal token new`를 실행합니다. 출력된 링크를 브라우저에서 승인하세요. 토큰은 `~/.letify/accounts/modal_lab/modal.toml`에 저장되므로 한 머신에 Modal 계정 두 개가 공존할 수 있습니다. `modal`을 `PATH`나 프로젝트 `.venv`에 직접 설치할 필요가 없습니다. 필요한 것은 uv뿐입니다.

Modal 볼륨은 컨테이너 밖에서 마운트되므로 저장소가 persistent이고, 기본이 함수 전송이며 별도 캐시 계층이 필요 없습니다. 샌드박스 안의 letify 파일은 프로젝트 `.venv`까지 모두 `/letify` 아래에 있고, 그 자리에 `<app>-workspace`라는 Modal 볼륨이 마운트되므로 다음 샌드박스가 그대로 찾습니다. 로그인할 때 `--workspace PATH`로 마운트 위치를 바꿀 수 있습니다.

`host="local"`은 예외를 던집니다. Modal은 컨테이너로 들어가는 함수 호출을 제공하고, PyTorch 연산을 중계할 장치를 제공하지 않습니다.

Modal 클라이언트는 letify가 첫 호출 때 띄우는 작은 어댑터 프로세스 안에서, Modal을 `>=1.0,<2`로 고정한 별도 uv 환경으로 실행됩니다. 처음 띄울 때 Modal을 uv 캐시에 내려받습니다. 셸의 `MODAL_TOKEN_ID`, `MODAL_TOKEN_SECRET`에 든 토큰은 무시됩니다. 어느 계정으로 동작할지는 그 계정의 `modal.toml`이 정합니다.

## 🇰🇷 Elice

```toml
[elice_a100]
kind = "elice"
zone_id = "00000000-0000-0000-0000-000000000000"
price_type = "spot"                 # 선택: ondemand(기본) 또는 spot
spot_fallback = "ondemand"          # 선택: none(기본) 또는 ondemand
access_token_env = "ELICE_ACCESS_TOKEN"
```

엘리스가 배포하는 명령줄 도구 `eci`로 Elice Cloud Infrastructure를 다룹니다. 처음 필요할 때 letify가 설치합니다. 미리 설치해도 됩니다.

```bash
letify setup eci                 # 엘리스의 릴리스를 내려받음
curl -fsSL https://raw.githubusercontent.com/elice-dev/eci-cli/main/scripts/install.sh | sh
```

letify가 어디에 설치하는지는 [tailcat과 eci 설치](#tailcat과-eci-설치)를 보세요.

**머신이 미리 있을 필요가 없습니다.** `letify login elice elice_a100`은 `eci`로 토큰을 확인하고, 머신이 없으면 아무 머신도 기록하지 않습니다. 첫 호출에서 letify가 선언에 맞는 인스턴스 타입으로 `letify-elice-a100`(spot이면 `letify-elice-a100-spot`)을 만듭니다. 생성한 비밀번호는 `~/.letify/accounts/elice_a100/machine_password`에 두고 SSH 키를 설치합니다. 다음 호출부터는 같은 머신을 다시 켭니다. 직접 만든 머신을 쓰려면 로그인할 때 고르거나 `machine_id`를 적으세요.

```python
elice = let.providers.elice_a100
elice.A100                    # 계정의 price type
elice.A100.priced("spot")     # 이 선언만 spot
```

세션이 끝나면 `eci compute vm stop`을 실행하고, letify는 아무것도 지우지 않습니다. 정지(idle)한 머신은 컴퓨트 요금이 없지만 디스크와 공인 IP는 계속 과금됩니다. 머신은 `eci compute vm delete <name> --cascade`로 지우세요. `--cascade` 없이 지우면 디스크, 네트워크 인터페이스, IP가 남아 계속 과금됩니다.

spot은 더 싸지만 엘리스가 언제든 머신을 회수할 수 있습니다. 그러면 letify는 `SpotPreempted`를 던지고, 이는 인프라 실패이므로 `retries`만큼 재시도됩니다. 머신 디스크와 볼륨의 파일은 남고, 메모리와 세션 캐시 핸들은 사라집니다. ondemand로 만들 때는 조직 쿼터를 먼저 확인하며, spot은 GPU 타입에만 제공됩니다.

엘리스의 다른 제품인 Run Box는 콘솔로만 제어되고 API가 없습니다. 그래도 터널 주소와 포트를 적어 평범한 `shell`로 선언하면 쓸 수 있습니다.

## 💻 Local

항상 있고 선언이 필요 없습니다. 전송 없이 이 머신의 서브프로세스에서 선언된 함수를 실행합니다.

```python
here = let.providers.local
here.CPU                      # 항상 있음
here.GeForce_RTX_4050         # nvidia-smi가 보고하는 것
```

두 가지 용도가 있습니다. GPU가 있으면 다른 것과 같은 선언으로 그걸 씁니다. 없어도 테스트가 목 객체 대신 실제 경로를 지나갑니다.

## 🔀 계정 여러 개

설정 항목 하나가 계정 하나이고, 같은 종류를 여러 개 둘 수 있습니다. 동시 세션을 늘리는 방법입니다.

```toml
[colab_a]
kind = "colab"
account = "first@example.com"

[colab_b]
kind = "colab"
account = "second@example.com"
```

```python
a = let.providers.colab_a
b = let.providers.colab_b

@let.function(device=a.G4, host="remote")
def train(lr): ...

@let.function(device=b.L4, host="remote")
def evaluate(ckpt): ...
```

한 계정에서 학습하고 다른 계정에서 평가하는 구성이 흔합니다. 긴 작업이 짧은 확인을 막지 않기 때문입니다.

## 🎲 프로바이더를 고르지 않기

```python
@let.function(device=let.providers.any.A100, host="remote")
def train(lr): ...
```

`A100`을 등록한 첫 프로바이더를 고릅니다. 우선순위는 설정 파일에 적힌 순서이니, 선호하는 프로바이더를 앞에 두세요.

## 🔍 살펴보기

```python
let.providers.aliases          # ['colab_a', 'lab_a100', 'local']
let.providers.devices             # 프로바이더별 GPU
let.providers.active           # 지금 런타임을 들고 있는 프로바이더
let.providers.colab_a.instances
let.providers.lab_a100.refresh()   # 머신에 다시 물어보기
```

`let.providers.active`는 지금 돈이 나가고 있는지에 대한 가장 빠른 답입니다.

```bash
letify providers
letify devices
letify status
letify check lab_a100
```

## tailcat과 eci 설치

letify는 직접 배포하지 않는 프로그램 두 개를 실행합니다. Tunnel 계정에는 Tailscale의 `tailcat`, Elice 계정에는 엘리스의 `eci`입니다. 둘 다 letify의 일부가 아니며 letify의 라이선스가 적용되지 않습니다. 명령에 필요한데 찾지 못하면 letify가 설치하고 표준 오류에 두 줄을 출력합니다.

```
letify: installing tailcat 0.6.0 from https://github.com/tailscale/tailcat/releases/download/v0.6.0/tailcat_0.6.0_linux_amd64.tar.gz into ~/.letify/tools/tailcat/0.6.0
letify: tailcat 0.6.0 verified sha256 f3597a9a..., linked at .venv/bin/tailcat
```

미리 설치하거나 letify가 무엇을 쓰는지 보려면:

```bash
letify setup tailcat          # 지금 설치
letify setup eci --where      # 어디에 있고 letify가 어느 복사본을 쓰는지
```

자동 설치를 끄려면 `~/.letify/config.toml` 맨 위에 `auto_install = false`를 적거나 `LETIFY_AUTO_INSTALL=0`을 설정하세요. 그러면 도구가 없을 때 설치 방법과 `letify setup <tool>` 명령을 출력하고 실패합니다.

설치는 이렇게 진행됩니다.

1. 배포처의 GitHub 릴리스(`tailscale/tailcat` 또는 `elice-dev/eci-cli`)에서 고정된 버전의 압축 파일을 내려받습니다.
2. SHA-256을 letify에 고정된 값과 릴리스의 `checksums.txt`에 모두 대조하고, 다르면 거부합니다.
3. `~/.letify/tools/<tool>/<version>/`에 풀고, 그 디렉터리 밖을 가리키는 항목이 있으면 압축 파일 전체를 거부합니다.
4. 프로젝트의 `.venv/bin`에 연결합니다. `tailcat`은 하드 링크(불가능하면 복사), `eci`는 작은 실행 스크립트입니다.

letify는 `~/.local/bin`, `/usr/local/bin`, 셸 프로필에 쓰지 않습니다. `PATH`에 직접 설치한 복사본은 그대로 쓰고 바꾸지 않으며, letify가 만들지 않은 `.venv/bin`의 파일은 건드리지 않습니다. Homebrew가 있는 macOS에서는 `tailcat`을 `brew install tailcat`으로 설치합니다.
