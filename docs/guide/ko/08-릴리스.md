# 릴리스

릴리스는 버전 번호 하나를 `v<version>` 태그로 푸시하는 것입니다. GitHub Actions가 모든 결과물을 빌드해 GitHub Release에 첨부합니다.

## 버전 규칙

`pyproject.toml`의 `[project].version`이 기준입니다. `letify/__init__.py`, `letify-core/Cargo.toml`과 `Cargo.lock`, `letify-ext/package.json`과 `package-lock.json`은 같은 값을 가집니다. 직접 고치지 마세요:

```
python scripts/version.py show            # 파일별 버전 출력
python scripts/version.py set 1.2.0       # 모든 파일에 1.2.0 기록
python scripts/version.py check           # 어긋난 파일이 있으면 exit 1
python scripts/version.py check --tag v1.2.0
```

`ci` 워크플로가 모든 푸시와 풀 리퀘스트에서 `check`를 실행합니다.

## 절차

1. 테스트가 통과하는 `develop`에서 버전을 정하고 커밋합니다:

   ```
   python scripts/version.py set 1.2.0
   git commit -am "Chore: Set the version to 1.2.0"
   ```

2. 평소처럼 커밋을 `main`에 반영한 뒤, 그 커밋에 태그를 달아 푸시합니다:

   ```
   git tag v1.2.0
   git push origin v1.2.0
   ```

3. `publish` 워크플로가 실행됩니다. 태그와 파일이 어긋나면 먼저 실패합니다. 그렇지 않으면 다음을 빌드합니다:
   - sdist
   - letify-core 바이너리를 담은 플랫폼 휠 6개
   - 확장 단위 테스트 통과 후 `letify-ext-1.2.0.vsix`

4. 이 파일을 모두 첨부한 GitHub Release `v1.2.0`을 만들고, sdist와 휠은 trusted publishing으로 PyPI에 올립니다.

5. 같은 태그에서 `publish-crates` 워크플로가 실행됩니다. `verify` 작업은 버전 파일, 태그된 커밋이 `develop`에 있는지, 워크스페이스 빌드와 테스트, `cargo publish -p letify --dry-run`을 확인합니다. 그다음 `publish-crate` 작업이 crate `letify` 1.2.0을 crates.io에 올립니다. 그 버전이 이미 있으면 올리지 않고 그 사실을 알린 뒤 성공으로 끝납니다. crates.io는 버전을 교체하지 않으므로 잘못 올린 버전은 yank만 할 수 있습니다.

## crates.io 최초 설정

1. crates.io에서 `publish-new`와 `publish-update` 권한을 가진 API 토큰을 만들고, crate 패턴을 `letify`와 `letify-*`로 제한합니다.
2. GitHub 저장소 설정에서 `crates-io`라는 이름의 environment를 만듭니다.
3. 그 environment에 토큰을 시크릿 `CARGO_REGISTRY_TOKEN`으로 추가합니다.
4. 선택 사항으로 environment에 필수 리뷰어를 추가하면, crates.io 업로드마다 승인을 기다립니다.

3번 전에 푸시한 태그는 `verify`를 통과한 뒤 업로드 단계에서 없는 시크릿을 알리며 실패합니다. 아무것도 게시되지 않습니다.

실행이 실패하면 Release에는 아무것도 올라가지 않습니다. 원인을 고치고 `git push origin :v1.2.0`으로 태그를 지운 뒤 다시 태그합니다.

## 릴리스에서 확장 설치

Release 페이지에서 `.vsix`를 받아 `code --install-extension letify-ext-1.2.0.vsix`를 실행합니다. 확장은 VS Code Marketplace에 올라가 있지 않습니다. 올리려면 `vsce publish` 단계와 저장소 시크릿으로 둔 Marketplace 토큰이 필요합니다.
