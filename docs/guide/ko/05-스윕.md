## 루프가 아니라 공간을 선언합니다

스윕은 값입니다. 스칼라가 올 자리에 넘기면 그 인자가 변한다는 선언이 됩니다.

```python
space = letify.grid(lr=[1e-4, 3e-4, 1e-3], bs=[16, 32])   # 6개
pairs = letify.zip(lr=[1e-4, 3e-4], bs=[16, 32])          # 2개
```

| 생성자 | 하는 일 | 쓰는 곳 |
|---|---|---|
| `grid` | 축의 데카르트 곱 | 하이퍼파라미터 탐색 |
| `zip` | 축을 위치별로 짝지음 | 미리 정한 설정 목록 |
| `a | b` | 합집합, 중복 제거 | 두 탐색 합치기 |
| `space.with_fixed(**kw)` | 모든 점에 공통인 인자 추가 | epoch, 시드, 출력 경로 |

스칼라 축은 고정되므로 `grid(lr=[1e-4, 3e-4], bs=32)`는 2개입니다.

`zip`은 길이가 다른 축을 조용히 자르지 않고 거부합니다.

```python
letify.zip(lr=[1e-4, 3e-4, 1e-3], bs=[16, 32])
# ValueError: zip axes must have equal length, got lr=3, bs=2
```

## 공간 소비하기

원할 수 있는 두 가지 순서가 이미 파이썬에 있습니다.

```python
@let.function(device=colab.G4, host="remote")
async def train(lr, bs):
    ...
    return {"lr": lr, "bs": bs, "loss": loss}

results = await train(space)          # 입력 순서대로 리스트

async for result in train(space):     # 끝나는 대로 하나씩
    print(result)
```

`await`는 입력 순서로 모으므로 결과 표를 만들 때 맞습니다. `async for`는 완료 순서로 주므로, 스윕이 한 시간 걸릴 때 기다리는 대신 먼저 끝난 것을 보고 싶을 때 맞습니다.

동기 선언은 입력 순서 리스트를 돌려줍니다.

```python
@let.function(device=colab.G4, host="remote")
def train(lr, bs): ...

rows = train(space)     # 리스트
```

## 폭은 인벤토리에서 나옵니다

스윕이 얼마나 넓게 도는지를 선언에서 말하지 않습니다. 프로바이더 항목이 그 계정이 무엇을 가졌는지
선언하고, 그것이 답입니다.

```toml
[colab_pro.devices]
G4 = { count = 2 }            # 이 계정은 세션 두 개

[lab_a100.devices]
A100 = { indices = "0-3" }    # 공용 머신의 네 장이 우리 것
```

6개 조합을 카드 네 장에 나누면 벽시계 시간이 약 4분의 1이 됩니다. 크레딧 총량은 같습니다. GPU 네 개를
15분 쓰는 것과 하나를 한 시간 쓰는 것이 같기 때문입니다.

> ⏱️ **연구에서는 벽시계 시간에 돈을 낼 가치가 있습니다.** 결과를 네 배 빨리 보면 다음 실험을
> 설계하는 속도가 달라집니다. 크레딧 총량은 그대로여도 그렇습니다.

두 번째 숫자는 없습니다. 선언의 폭과 런처의 상한은 한 결정을 두 번 말하는 것이었고, 둘이 어긋나면
작은 쪽이 조용히 이겼습니다. 스윕이 느린데 어느 숫자도 이유를 말해주지 않았습니다.

## 카드를 두 장 쓰는 실행

인스턴스를 곱합니다.

```python
@let.function(device=lab.A100 * 2, host="remote")
def train(lr):
    ...
```

위의 네 장짜리 머신에서 이것은 세션 네 개가 아니라 두 개입니다. 폭을 정하는 숫자가 성립할 수 없는
이유가 바로 이것입니다. 세션이 몇 개까지 존재할 수 있다는 숫자는 각 세션이 카드를 몇 장 필요로 하는지에
대해 아무 말도 하지 않습니다.

세션은 자기 가시 장치를 직접 설정하므로, 안의 코드는 자기 카드를 `cuda:0`과 `cuda:1`로 보고 물리 인덱스가
무엇이었는지 알 필요가 없습니다.

## 머신을 다른 사람과 함께 쓸 때

학과 공용 머신에서는 쓸 수 있는 인덱스가 누가 접속해 있는지에 따라 바뀝니다. 내 것인 인덱스를 등록해
두면, letify는 세션이 시작되는 시점에 그중 실제로 비어 있는 것만 가져갑니다.

```toml
[lab_a100.devices]
A100 = { indices = "0-3" }
```

동료가 연산 중인 카드는 건드리지 않고 넘어갑니다. 사용률이 아니라 연산 프로세스를 읽습니다. 스텝 사이의
카드는 유휴로 보이지만 유휴가 아니기 때문입니다. letify는 무엇도 죽이지 않고, 등록하지 않은 인덱스는
건드리지 않습니다.

## 실제로 몇 개가 떴는지

```python
print(let.status()["devices"])   # 인벤토리 대비 예약된 수
print(let.status()["live"])      # 지금 존재하는 세션 수
```

```bash
letify status
```

스윕이 기대보다 좁으면 볼 곳은 인벤토리뿐입니다. 카드를 예약하지 못한 지점은, 프로바이더가 거절할
머신을 요청하는 대신 실행 중인 지점이 끝나기를 기다립니다. 실행 중인 무엇도 카드를 풀어주지 않으면
끝없이 기다리지 않고 `letify.InsufficientDevices`가 발생합니다.

카드를 더 얻는 방법은 계정을 늘리는 것입니다. 인벤토리는 계정 하나에 속하기 때문입니다.
[프로바이더와 계정](02-프로바이더.md)을 보세요.

## 더 싼 GPU를 더 많이

탐색 단계에서는 각각이 얼마나 빠른지보다 동시에 몇 개가 도는지가 더 중요한 경우가 많습니다.

| GPU | 시간당 | 세 개 동시 |
|---|---|---|
| A100 80GB | 약 841원 | 2,523원 |
| L4 | 약 191원 | 573원 |

L4 세 개가 A100 하나보다 시간당 싸면서, A100 하나가 조합 하나를 끝내는 시간에 세 개를 끝냅니다. 작업이 22GB에 들어가면, 하이퍼파라미터 탐색은 배치를 줄이면 들어가는 경우가 많고, 이쪽이 더 나은 교환입니다.

최종 후보만 큰 카드에서 확인하세요.

> ⚠️ 특정 기능이 필요할 때는 해당되지 않습니다. NVFP4는 블랙웰 텐서 코어가 필요하고, Colab에서는 `G4`뿐입니다. 더 싼 대체가 없습니다.

## 실용 패턴

**공간을 돌려 표로 모으기.**

```python
rows = await train(letify.grid(lr=[1e-4, 3e-4, 1e-3], bs=[16, 32]))

best = min(rows, key=lambda r: r["loss"])
print(best)
```

**결과가 오는 대로 기록하기.**

```python
async for row in train(space):
    wandb.log(row)
```

**서로 다른 프로바이더에서 학습과 평가를 동시에.**

```python
@let.function(device=colab.G4, host="remote")
async def train(lr): ...

@let.function(device=lab.A100, host="remote")
async def evaluate(ckpt): ...

await asyncio.gather(train(lr=1e-4), evaluate(ckpt="run-1"))
```

선언마다 자기 인스턴스를 지정하니, 하나는 Colab에서 다른 하나는 연구실 서버에서 추가 장치 없이 돕니다.

**평가 배치가 GPU 추가보다 중요합니다.** 초당 12.5프레임인 음성 모델이라면 10초 발화가 125프레임입니다. 배치 1에 프레임당 20ms면 100발화에 250초입니다. 배치 64면 같은 평가가 5~10초입니다. 500스텝마다 평가한다면 오버헤드 100%와 3%의 차이입니다.
