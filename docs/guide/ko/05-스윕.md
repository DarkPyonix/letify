## 루프가 아니라 공간을 선언합니다

스윕은 값입니다. 스칼라가 올 자리에 넘기면 그 인자가 변한다는 선언이 됩니다.

```python
space = letify.grid(lr=[1e-4, 3e-4, 1e-3], bs=[16, 32])   # 6개
pairs = letify.zip(lr=[1e-4, 3e-4], bs=[16, 32])          # 2개
```

| 생성자 | 하는 일 | 쓰는 곳 |
|---|---|---|
| `grid` | 축의 데카르트 곱 | 하이퍼파라미터 탐색 |
| `zip` | 축을 위치별로 짝지음 | 미리 정한 설정 목록 |
| `a | b` | 합집합, 중복 제거 | 두 탐색 합치기 |
| `space.with_fixed(**kw)` | 모든 점에 공통인 인자 추가 | epoch, 시드, 출력 경로 |

스칼라 축은 고정되므로 `grid(lr=[1e-4, 3e-4], bs=32)`는 2개입니다.

`zip`은 길이가 다른 축을 조용히 자르지 않고 거부합니다.

```python
letify.zip(lr=[1e-4, 3e-4, 1e-3], bs=[16, 32])
# ValueError: zip axes must have equal length, got lr=3, bs=2
```

## 공간 소비하기

원할 수 있는 두 가지 순서가 이미 파이썬에 있습니다.

```python
@let.function(device=colab.G4, host="remote", concurrency=3)
async def train(lr, bs):
    ...
    return {"lr": lr, "bs": bs, "loss": loss}

results = await train(space)          # 입력 순서대로 리스트

async for result in train(space):     # 끝나는 대로 하나씩
    print(result)
```

`await`는 입력 순서로 모으므로 결과 표를 만들 때 맞습니다. `async for`는 완료 순서로 주므로, 스윕이 한 시간 걸릴 때 기다리는 대신 먼저 끝난 것을 보고 싶을 때 맞습니다.

동기 선언은 입력 순서 리스트를 돌려줍니다.

```python
@let.function(device=colab.G4, host="remote", concurrency=3)
def train(lr, bs): ...

rows = train(space)     # 리스트
```

## 병렬도는 선언에 속합니다

```python
@let.function(device=colab.G4, host="remote", concurrency=3)
```

이 선언이 동시에 쓸 수 있는 런타임 수이고, 개별 호출의 속성이 아닙니다. 그 선언이 사용해도 되는 인프라를 설명하는 것이라 선언에 있습니다.

6개 조합을 세 런타임에 나누면 벽시계 시간이 약 3분의 1이 됩니다. 크레딧 총량은 같습니다. GPU 세 개를 30분 쓰는 것과 하나를 90분 쓰는 것이 같기 때문입니다.

> ⏱️ **연구에서는 벽시계 시간에 돈을 낼 가치가 있습니다.** 결과를 세 배 빨리 보면 다음 실험을 설계하는 속도가 달라집니다. 크레딧 총량은 그대로여도 그렇습니다.

## 런타임을 실제로 몇 개 받을 수 있나

두 가지 한도가 있고 서로 다릅니다.

선언의 `concurrency`는 그 선언이 쓸 수 있는 수입니다. 런처의 `max_runtimes`는 프로세스 전체의 상한입니다.

```python
let = letify.Launcher(max_runtimes=4)
```

```toml
[defaults]
max_runtimes = 4
```

프로바이더 자체의 한도도 있고, Colab의 경우 문서화되어 있지 않으며 등급과 크레딧 잔액과 그때의 수요에 따라 바뀝니다. 기본값 3은 추정치입니다. 재보세요.

```python
let = letify.Launcher(max_runtimes=6)

@let.function(device=colab.L4, host="remote", concurrency=6)
async def probe(n):
    return n

await probe(letify.grid(n=list(range(6))))
print(len(let.pool.live))        # 실제로 몇 개가 떴는지
```

이 측정에는 `L4`를 쓰세요. 가장 싼 GPU라서 한도를 찾는 비용이 거의 없습니다.

한도는 계정별이니, 계정을 늘리는 것이 상한을 올리는 다른 방법입니다. [프로바이더와 계정](02-프로바이더.md)을 보세요.

## 더 싼 GPU를 더 많이

탐색 단계에서는 각각이 얼마나 빠른지보다 동시에 몇 개가 도는지가 더 중요한 경우가 많습니다.

| GPU | 시간당 | 세 개 동시 |
|---|---|---|
| A100 80GB | 약 841원 | 2,523원 |
| L4 | 약 191원 | 573원 |

L4 세 개가 A100 하나보다 시간당 싸면서, A100 하나가 조합 하나를 끝내는 시간에 세 개를 끝냅니다. 작업이 22GB에 들어가면, 하이퍼파라미터 탐색은 배치를 줄이면 들어가는 경우가 많고, 이쪽이 더 나은 교환입니다.

최종 후보만 큰 카드에서 확인하세요.

> ⚠️ 특정 기능이 필요할 때는 해당되지 않습니다. NVFP4는 블랙웰 텐서 코어가 필요하고, Colab에서는 `G4`뿐입니다. 더 싼 대체가 없습니다.

## 실용 패턴

**공간을 돌려 표로 모으기.**

```python
rows = await train(letify.grid(lr=[1e-4, 3e-4, 1e-3], bs=[16, 32]))

best = min(rows, key=lambda r: r["loss"])
print(best)
```

**결과가 오는 대로 기록하기.**

```python
async for row in train(space):
    wandb.log(row)
```

**서로 다른 프로바이더에서 학습과 평가를 동시에.**

```python
@let.function(device=colab.G4, host="remote", concurrency=1)
async def train(lr): ...

@let.function(device=lab.A100, host="remote", concurrency=1)
async def evaluate(ckpt): ...

await asyncio.gather(train(lr=1e-4), evaluate(ckpt="run-1"))
```

선언마다 자기 인스턴스를 지정하니, 하나는 Colab에서 다른 하나는 연구실 서버에서 추가 장치 없이 돕니다.

**평가 배치가 GPU 추가보다 중요합니다.** 초당 12.5프레임인 음성 모델이라면 10초 발화가 125프레임입니다. 배치 1에 프레임당 20ms면 100발화에 250초입니다. 배치 64면 같은 평가가 5~10초입니다. 500스텝마다 평가한다면 오버헤드 100%와 3%의 차이입니다.

## 호출당 공간은 하나만

```python
train(letify.grid(lr=[1e-4]), letify.grid(bs=[16]))
# TypeError: only one search space may be passed per call.
#            Combine them with let.grid(...) or the | operator instead.
```

축을 한 공간으로 합치세요. 그러면 점의 개수가 두 인자의 곱이 아니라 한 곳에 보입니다.
